Dline 使用一个统一的 `TelemetryService` pipeline 处理 Events、Metrics、Traces、runtime/error 事件和本地诊断数据。所有输出都先经过 channel consent 与内容策略；开发模式只增加诊断信息，不会替用户授权遥测。

## Consent 合同

在 **Dline Settings → About** 中有两个独立开关：

| 设置 | 内部键 | 负责的 channel | 典型信号 |
| --- | --- | --- | --- |
| Allow usage reporting | `usageReportingSetting` | `usage` | 产品使用事件、token/cost/tool 等业务 metrics、gRPC response size |
| Allow error reporting | `errorReportingSetting` | `error`、`runtime`、`raw-artifact` | 错误事件、runtime anomaly、operation spans、runtime gauges、诊断导出 |

每个设置都有三种状态：

- `enabled`：对应 channel 可以写入本地 Journal，并发送给已配置的 provider。
- `unset`：用户尚未作出选择，按未授权处理。
- `disabled`：明确禁止对应 channel。

当对应设置是 `unset` 或 `disabled` 时：

- 不 materialize signal properties；
- 不创建对应本地 Journal 文件；
- 不调用 loopback 或 remote exporter；
- bootstrap 中尚未获得授权的 Event、Metric、Gauge 和已结束 Span 会被丢弃，不会在之后重新授权时补发。

`required`、`logRequired`、organization 配置或 remote sink 都不能绕过 consent。`required` 只保留已授权信号在 provider 内的顺序语义。

<Warning>
`IS_DEV=true` 和 `TEL_DEBUG_DIAGNOSTICS=true` 只启用更详细的 exporter 调试信息。它们不会把 `unset` 或 `disabled` 变成 `enabled`，也不会授权写盘或联网。
</Warning>

## 默认 OTLP collector

在对应 channel 已授权时，默认 OpenTelemetry provider 使用本机 loopback collector：

```text
http://127.0.0.1:4318
```

HTTP/protobuf signal endpoints 为：

```text
/v1/logs
/v1/metrics
/v1/traces
```

Dline 使用 scoped `LoggerProvider`、`MeterProvider` 和 `TracerProvider`，不注册 process-global OpenTelemetry provider。这样 consent 驱动的 provider 重启不会被 OpenTelemetry 的 first-wins global registration 阻塞。

### Exporter 日志级别

高频、成功和状态类 OTLP 输出只使用 debug 级别，例如：

```text
[debug] [OTEL LOGS] Export #3 OK - protocol=http/protobuf ...
[debug] [OTEL METRICS] Export #1 OK - protocol=http/protobuf ...
```

它们不会再以普通 `[log]` 级别刷屏。创建 provider、reader、exporter 和 instrument 的正常状态同样使用 debug。export failure、exception、未知协议和配置错误仍使用 warning/error 级别。

若需要这些调试输出，可在开发环境设置：

```text
IS_DEV=true
```

或只启用 exporter diagnostics：

```text
TEL_DEBUG_DIAGNOSTICS=true
```

## Metric 命名

Canonical metric 名统一使用 `dline.` 前缀。例如源 metric：

```text
dline.grpc.response.size_bytes
```

经 Prometheus 命名转换后，histogram bucket 显示为：

```text
dline_grpc_response_size_bytes_bucket
```

旧的 `cline_*` metric namespace 不再由当前实现发送。更新 dashboard、alert 和 recording rule 时，应迁移到 `dline_*`。

每个完成且有精确 usage 的 provider request 会更新以下低基数 metrics：

```text
dline_api_requests_total
dline_tokens_total
dline_cache_input_tokens_total
dline_cache_read_tokens_total
dline_cache_hit_rate_percent_bucket|sum|count
```

Prometheus 中可按窗口派生：

```promql
# RPM
sum(rate(dline_api_requests_total[1m])) * 60

# TPM（input + output + cache read/write + reasoning）
sum(rate(dline_tokens_total[1m])) * 60

# token-weighted cache hit percentage
100 * sum(rate(dline_cache_read_tokens_total[5m]))
  / sum(rate(dline_cache_input_tokens_total[5m]))
```

这些 metrics 不携带高基数 `distinct_id`。按单个 Dline 安装排查时，应在 Loki 中筛选 usage `task.tokens` LogRecord 的 `distinct_id`。

## 本地 Journal

授权后，LocalJournalProvider 在 Dline data directory 下写入：

```text
telemetry/sessions/usage-<sessionId>.jsonl
telemetry/sessions/metrics-<sessionId>.jsonl
telemetry/sessions/traces-<sessionId>.jsonl
```

- Event 写入 `usage-*.jsonl`；记录仍携带原始 channel（`usage`、`error`、`runtime` 或 `raw-artifact`）。
- Metric 与 Gauge 写入 `metrics-*.jsonl`。
- 已结束 Span 写入 `traces-*.jsonl`。
- 每条记录包含 build、schema、session、sequence、channel、signal kind 和 content-policy metadata。
- 文件使用 OTLP JSON resource envelope，便于离线分析而不依赖 collector。

Journal 目录按需创建：仅构造 provider、恢复应用或保持 consent 未授权不会创建目录。单个文件有界；达到上限时保留较新的有效记录。启动恢复会截断不完整尾行、报告 sequence gap，并从最后有效 sequence 继续编号。

WS-017 runtime diagnosis 仍维护独立的 session journal：

```text
telemetry/sessions/<sessionId>.jsonl
```

它服务于 runtime root-cause analysis 与 diagnostic export，不替代 LocalJournalProvider 的 usage/metrics/traces 文件。

## OTLP Logs 字段位置

OTLP LogRecord 的 `body` 只保存稳定事件名，例如 `extension.message` 或 `runtime.operation.failed`。可查询的结构化字段位于 LogRecord attributes；经当前 collector 写入 Loki 后显示为 `structuredMetadata`。因此只查看日志正文时，看不到 provider、model、tokens 或 snapshot 信息并不表示这些字段未发送。

内容策略会递归展平安全对象和数组，例如：

- `provider`、`modelId`、本次 request 实际 selected `apiFormat`；
- `extension_version`、`vscode_version` 与平台版本；
- `tokens.input`、`tokens.output`、cache/cost 数值；
- `requestsPerMinute`、`tokensPerMinute`、`cacheHitRate` 与 `features.*`；
- `model_list[]`、`capabilities[]`；
- `snapshot.phase/status/count/durationMs`；
- `operation`、`outcome`、`telemetry_channel`、`telemetry_severity`。

在 Loki 中，它们会显示为 `tokens_input`、`model_list_0`、`snapshot_status` 等可独立筛选的 structured metadata。

### 区分当前与旧 extension-host 的严重度

普通 performance sample（包括成功的 `settings.controller_callback`）使用 `INFO`；只有 threshold breach/degraded condition 使用 `WARN`，明确失败使用 `ERROR`。如果同一事件同时出现 INFO 与 WARN，不要只按事件名判断当前实现：先比较 structured metadata 中的 `service_version`、`scope_name` 和 `service_instance_id`。

开发环境可能同时保留多个尚未 reload 的 VS Code extension-host。旧 host 会继续使用其已加载的 telemetry bundle，并可能发送旧 severity 映射。确认当前 `extension_version` 的记录已经为 INFO 后，reload 仍发送旧版本记录的窗口；历史 WARN 不会被新构建追溯改写。

## 隐私与内容策略

LocalJournal、runtime compatibility transport 与正式 OpenTelemetry provider 使用一致的递归展平和字段级内容策略。策略保留字段名，避免只剩事件名或无法判断字段为何缺失：

- 安全运行元数据保留真实值，包括版本、provider/model/API format、数值型 token/cache/cost、RPM/TPM、cache hit、feature enablement、model list、capabilities、snapshot 状态、operation 与 outcome；
- prompt、message、command、output、result、response、文件内容和 exception prose 保留字段名，但值统一替换为 `*****`；
- API key、OAuth/access token、authorization、password、cookie、secret 和其他 credential 保留字段名，但值统一替换为 `*****`；
- user、organization、member、task、workspace、controller、email、username 等 identity 保留字段名，但值统一替换为 `*****`；
- dotted key 使用完整路径与叶名检查，因此 `nested.prompt`、`exception.message` 不能绕过策略；
- `sessionId` 保留用于单次 extension-host session 内关联；error fingerprint 使用不可逆 SHA-256 截断 hash，不包含 exception message；
- `identifyUser` payload 不写入 LocalJournal；diagnostic bundle 在最终写出边界再次执行深度 redaction 和 secret pattern scrub。

`distinct_id` 是唯一按 channel 分级的 identity 例外：`usageReportingSetting === enabled` 时 usage OTLP Event 附加明文 `distinct_id`，`errorReportingSetting === enabled` 时 error/runtime OTLP Event 附加；两个 channel 可独立关闭。未授权 channel 不产生记录，因此也不发送 `distinct_id`。该字段不进入 Prometheus labels，单个 Dline 的 RPM/TPM/cache hit 与 feature 状态通过 Loki `task.tokens` structured metadata 查询。

<Note>
开启 reporting 表示允许发送经过策略处理的结构化遥测，不表示允许发送 prompt、模型输出、命令正文、文件内容、凭据或用户身份原文。数值型 token usage 与 credential token 是不同类别：前者是安全计量元数据，后者始终掩码。
</Note>

## Delivery accounting

OTLP logs 和 metrics exporter 安装统一 delivery-accounting decorator。统计只基于 exporter callback 边界：

- enqueued batch/record；
- exported batch/record；
- failed batch/record；
- timed-out batch/record。

OpenTelemetry SDK 内部 retry 次数和 queue overflow 没有稳定 public callback，因此明确标记为 `unobservable`，不会通过反射或依赖 SDK 私有队列伪造精确数字。

## Diagnostic export

只有 `errorReportingSetting === enabled` 时，Settings 才显示 diagnostic export。导出操作使用 WS-017 session events、root-cause diagnoses、环境摘要和用户显式选择的 artifact 构建本地 bundle。

导出不会自动上传；bundle 写入前会再次进行字段级和文本级 redaction。若导出失败，临时文件会尽力清理，并返回可操作错误。

## 排查没有 Traces

1. 确认 **Allow error reporting** 为 enabled；operation spans 属于 `runtime` channel。
2. 确认 collector 正在监听 `127.0.0.1:4318`，并启用了 OTLP HTTP receiver。
3. 执行可产生 operation span 的行为，例如工具调用、等待批准或 snapshot operation。
4. 临时启用 `TEL_DEBUG_DIAGNOSTICS=true`，确认 `/v1/traces` export 被触发。
5. 在 Tempo 中按最近时间窗口查询；注意无操作时不会为了“证明存活”持续生成空 Span。

如果 debug 日志显示 exporter 成功但 Tempo 无数据，检查 collector 的 traces pipeline、exporter 和 tenant/routing 配置。若 debug 日志完全没有 trace export，优先检查 consent 与 provider lifecycle，而不是先检查 Tempo。

## 排查没有 Metrics

1. 对产品使用 metrics（例如 `dline_grpc_response_size_bytes`）确认 **Allow usage reporting** 为 enabled。
2. 对 runtime gauges/anomaly duration 确认 **Allow error reporting** 为 enabled。
3. 确认 collector metrics pipeline 与 Prometheus remote write/exporter 正常。
4. 查询 `dline_*`，不要继续查询已退役的 `cline_*`。
5. Histogram 在 Prometheus 中会展开为 `_bucket`、`_sum` 和 `_count` series。

空 export batch 的 `count=0` debug 输出不代表业务 metric 已生成；它只表示 SDK 到达了一次 export 周期。

## 排查没有本地文件

当对应 consent 是 `unset` 或 `disabled` 时，没有 Journal 目录或文件是预期行为。不要通过 `IS_DEV`、organization policy 或 remote provider 强制生成文件。

当 consent 已启用但仍无文件：

1. 先执行至少一个属于该 channel 的操作；目录是按首次授权写入创建的。
2. 等待周期 flush，或正常关闭 Dline 触发 provider dispose/flush。
3. 检查 Dline data directory 的写权限和磁盘空间。
4. 检查 error 日志中的 journal append、flush、retention 或 recovery 失败。

## 开发验证

修改 telemetry pipeline 后，至少运行相关 Vitest、类型检查、lint 和 compile。runtime E2E 必须通过项目封装入口运行：

```bash
npm run e2e -- runtime-telemetry
```

不要直接调用裸 Playwright 命令，因为项目入口负责配置 VS Code 测试环境、profiles 和结果目录。
